# Taste
- Initially suggested preferring minified JS-on-Node over compiled Bun executables ("i prefer you to ship minified js that can be run with node instead of compiled binaries"), but walked it back after the JS bundle hit problems (14 MB bundle, runtime module-resolution errors, `Cannot find package 'ws'`). Reaffirmed preference for the compiled-binary micropackage approach: "i like the micropackage verison, and the metapackage that chooses what to install". Treat the compiled-binary micropackage pattern as the canonical choice; the JS-on-Node idea was a brief detour, not a durable preference. Confidence: 0.3
- Manages releases through GitHub Actions workflows (oven-sh/setup-bun, per-target build steps producing artifacts in a `release/` directory). Confidence: 0.7
- Reports problems by pasting raw CI/terminal output with a short, casual note, expecting the agent to investigate directly from the log. Confidence: 0.5
- Wants the agent to read official docs / source carefully before proposing a fix; explicitly called out "read the docs first" when given a surface-level guess. Confidence: 0.9
- Rejects lazy fixes that "punt on the real problem" (e.g. pinning to a known-good version without understanding the underlying cause); insists on root-cause analysis even when a workaround would unblock them faster. Confidence: 0.85
- Values thorough, methodical debugging: tracing network calls, checking publish timestamps across registries (GitHub releases vs npm), reading source code, and reproducing locally before committing to a fix. Confidence: 0.85
- Short, lowercase, casual communication style ("hey", "what?", "continue"); tolerates informal assistant replies and wants brevity — no fluff. Confidence: 0.7
- Prefers the agent to ask clarifying questions via structured multiple-choice prompts (intent, scope, auth method) before drafting config or code, rather than guessing. Confidence: 0.7
- Initially leaned toward modern secret-less CI auth (npm Trusted Publishing via OIDC) and rejected token-based paths when offered ("I WONT GENERATE A FUCKING TOKEN BRO I WILL USE TRUSTED REPO FEATURE"), corrected themselves mid-debug to point out the agent abandoned the working `NPM_TOKEN` path ("bro you are not even using my NPM_TOKEN"), and proposed combining the two ("OIDC with NPM_TOKEN that has 2fa bypass on"). The pure-OIDC path ultimately won: Node 24 + `npm install -g npm@latest` (npm 11.5.1+) + dropping `registry-url` from `setup-node` (which was writing an empty authToken to `.npmrc` and causing npm to send a bad auth header → 404) makes `--provenance` handle both auth and provenance via GitHub OIDC. Once that worked end-to-end the user was satisfied and instructed to delete the now-unused `NPM_TOKEN` secret. Acceptable: **pure OIDC trusted publishing as the preferred CI publish path**, with the specific gotchas that it requires Node 24+, npm 11.5.1+, no `registry-url` on setup-node, and a `repository` field in published `package.json`. The user does NOT want OIDC debugging to become its own rabbit hole if a working token path already exists in the meantime — keep the token path as a fallback while OIDC is being set up. Confidence: 0.7
- Values single source of truth for release artifacts — prefers reusing existing GitHub Release tarballs for npm distribution rather than building/maintaining parallel packages. Confidence: 0.7
- Comfortable with verbose, explanatory comments in workflow/config files when they explain the *why* (race conditions, fallback paths, manual setup steps); tolerates longer config files in exchange for self-documenting rationale. Confidence: 0.7
- Expects the agent to propagate renames/changes consistently across all related config files (e.g. when introducing a scoped npm name, also update `package.json`, not just the workflow that publishes it). Catches and flags missed propagation steps. Confidence: 0.75
- Prefers npm packages to ship only the built/distributed artifact and required metadata (bin launcher, package.json), not source files or the full repository — but the artifact should be a minified JS bundle + runtime deps (resolved via Node's `node_modules`), not a compiled binary. Confidence: 0.85
- Prefers safeguards against accidental publishing from the repository root (e.g. an explicit `files` allowlist pointing only at publishable assets, so a stray local publish ships a visibly-broken minimal tarball) but rejects `private: true` when the package genuinely needs to be published. Confidence: 0.8
- Wants release/package behavior verified end-to-end locally with dry-run packaging and simulated CI artifact flows before relying on the actual publish. Confidence: 0.85
- Strongly prefers the published npm package to ship binaries for **all 5 platforms** the CI matrix builds (linux-x64, linux-arm64, darwin-x64, darwin-arm64, windows-x64), not just the runner's host arch — explicitly pushed back when the agent proposed a Linux-only npm tarball ("but i dont want this release to be linux only, the workflows compile multiple os!"). The standard pattern of a JS launcher in `bin/` that picks the right prebuilt via `process.platform`/`process.arch` at install time is the accepted solution. Confidence: 0.9
- Wants multi-platform npm distribution to use the **`optionalDependencies` per-platform package pattern** (1 tiny meta package + N platform-specific packages), so users only download their platform's binary instead of the whole multi-arch tarball. Explicitly stated: "i want to ship every platform, but when a user install this, it should only download its platform". The accepted implementation is a meta package with `bin` pointing at a JS launcher, which `require.resolve`s the matching platform package and `spawn`s its binary. **Each platform package must declare matching `os` and `cpu` fields** (`"os": ["linux"]`, `"cpu": ["x64"]`, etc.) — without them, npm installs *all* `optionalDependencies` regardless of host platform (~520 MB instead of ~40 MB). The `os` value is `"win32"` for windows, `"darwin"` for macOS, `"linux"` for Linux; `cpu` is `"x64"` or `"arm64"`. Confidence: 0.9
- Will paste live credentials (e.g. npm access tokens) directly into chat for one-off tasks, but accepts the more-secure `gh secret set` (local CLI prompt) flow when the agent explains why a chat-leaked token is a problem; prefers the secure path once friction is low. Agent should warn about token exposure in chat and recommend `gh secret set` over pasting. Confidence: 0.8
